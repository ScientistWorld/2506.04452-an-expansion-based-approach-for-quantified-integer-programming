# Scientist Constraints

These are the things a future scientist must keep fixed when claiming an
improvement over this workspace.

## Benchmark Family

- Task: satisfiability solving for quantified integer programs.
- Benchmark family: QRandomParity instances generated by the local generator in `data/`.
- Scored settings: `n=100` and `n=200`, matching the experiment keys `qrandomparity_n100` and `qrandomparity_n200`.

## Data and Generation

- Use the provided QRandomParity generation code and keep the semantics of the benchmark unchanged.
- Do not alter the instance family to make parity constraints easier, reduce quantifier interaction, or otherwise simplify the satisfiability structure.
- Record the exact seeds and number of generated instances in any claimed improvement.
- If you expand beyond the current scored slice, do so in new experiment entries rather than silently changing the existing ones.

## Evaluation Contract

- Keep the evaluation path `scripts/evaluate.sh -> eval/evaluate.py` unchanged unless you are extending it in a backward-compatible way.
- Continue to report both `median_runtime_s` and `instances_solved` for each scored experiment.
- Improvements on runtime do not count if they are obtained by solving fewer instances.

## Resource and Comparison Discipline

- Compare on the same experiment names already used in `scoring/reference.json` and `scoring/scores.json`.
- Do not claim improvement by switching to a different dataset, easier split, or a smaller benchmark.
- If you use a different IP backend, document it and keep the rest of the benchmark fixed so the change is scientifically attributable.

## Out of Bounds

- Replacing QRandomParity with a different benchmark while keeping the same score entries.
- Changing the benchmark generator so the scored `n=100` and `n=200` settings become easier.
- Dropping `instances_solved` and scoring only runtime.
- Reporting numbers that were not produced by running the solver and evaluator in this workspace.
